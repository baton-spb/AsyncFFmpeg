# Руководство по внесению вклада (Contributing)

Приветствуются любые улучшения, исправления ошибок и предложения новых функциональных возможностей в `async-ffmpeg`.

---

## 1. Стратегия ветвления (Branching Strategy)

В репозитории используется модель Git Flow с двумя долгоживущими ветками:

- **`main`**: стабильная (production) ветка. Содержит исключительно готовые к релизу версии кода. Прямые коммиты запрещены. Слияния осуществляются только из `develop` перед выпуском новой версии с созданием аннотированного тега (`vX.Y.Z`).
- **`develop`**: ветка активной разработки. В неё интегрируются новые возможности и исправления через Pull Requests.
- **Вспомогательные ветки**:
  - `feature/<название>`: разработка новой функциональности (создаются от `develop`, сливаются в `develop`).
  - `fix/<описание>` или `bugfix/<описание>`: устранение ошибок (создаются от `develop`, сливаются в `develop`).
  - `hotfix/<описание>`: неотложные исправления для продакшна (создаются от `main`, сливаются в `main` и `develop`).

---

## 2. Процесс разработки

1. Склонировать репозиторий:
   ```bash
   git clone ssh://git@localhost:2222/6aton/AsyncFFmpeg.git
   cd AsyncFFmpeg
   ```
2. Создать рабочую ветку от актуального состояния `develop`:
   ```bash
   git checkout develop
   git pull origin develop
   git checkout -b feature/my-feature
   ```
3. Установить зависимости для разработки через менеджер `uv`:
   ```bash
   uv sync --extra dev
   ```
4. Внести изменения, соблюдая архитектурные принципы проекта.
5. Написать модульные или интеграционные тесты в каталоге `tests/`.
6. Убедиться в успешном прохождении всех локальных проверок качества.
7. Зафиксировать изменения с понятными сообщениями коммитов и отправить ветку в удалённый репозиторий.

## 3. Стандарты качества кода

Перед отправкой изменений обязательно выполнение всех автоматических проверок:

```bash
# Проверка форматирования и линтинга
uv run ruff check src/ tests/ examples/ docs/
uv run ruff format --check src/ tests/ examples/ docs/

# Проверка строгой статической типизации (Zero Any policy)
uv run mypy src/

# Запуск полного набора тестов с анализом покрытия
uv run pytest tests/ -v
```

## 4. Архитектурные правила и ограничения

1. **Zero Runtime Dependencies**:
   - В секции `dependencies` файла `pyproject.toml` не допускаются внешние пакеты.
   - Разрешено использование исключительно стандартной библиотеки Python 3.14+.
   - Внешние интеграции (например, `async-yt-dlp`) оформляются как опциональные зависимости (`optional-dependencies`).
2. **Строгая статическая типизация**:
   - Политика `Zero Any`: использование типа `Any` строго запрещено во всех публичных и внутренних сигнатурах.
   - Для всех моделей данных используются frozen dataclass со `slots=True` (`@dataclass(frozen=True, slots=True)`).
   - Обязательно указание типов всех аргументов и возвращаемых значений (`-> None` для процедур).
3. **Языковая политика**:
   - Все docstrings, комментарии к коду и документация составляются на русском языке в нейтральной форме (инфинитивы, безличные конструкции, 3-е лицо; без использования местоимений первого и второго лица).
   - Все идентификаторы (имена модулей, классов, методов, функций, переменных) именуются на английском языке по стандарту PEP 8.
4. **Кроссплатформенность**:
   - Пути к файлам нормализуются через `normalize_path_for_ffmpeg()` из `_compat.py`.
   - Запуск подпроцессов учитывает специфику платформ (флаг `CREATE_NO_WINDOW` для Windows, сигналы завершения для POSIX).
